# Thought Mate: базовая архитектура

## Цель

Thought Mate — расширяемая платформа для создания AI-ассистентов. В основе
системы лежат управляемый цикл агента, модель инструментов и независимый от
LLM-провайдера runtime. Первым продуктовым сценарием станет coding assistant,
при этом архитектура предусматривает развитие в универсального персонального
помощника.

## Основной принцип

Ядро агента не зависит от OpenRouter, конкретной модели или набора инструментов.
Внешние сервисы подключаются через внутренние интерфейсы и адаптеры.

```text
User input
    ↓
AgentLoop → ContextManager → ModelClient
    ↑                          ↓
    └──── ToolExecutor ← Tool calls
```

## Цикл агента

Один запуск обрабатывает один пользовательский запрос:

1. Собирается контекст и список доступных инструментов.
2. Выполняется запрос к модели.
3. Если модель вернула финальный ответ, запуск завершается.
4. Если модель запросила инструменты, их вызовы валидируются и выполняются.
5. Результаты добавляются в контекст, после чего цикл повторяется.

Цикл ограничивается политиками: числом итераций, количеством вызовов
инструментов, временем выполнения и бюджетом токенов или стоимости.

## Основные компоненты

### AgentLoop

Управляет выполнением одного запуска, переходами между вызовами модели и
инструментов, остановкой, ошибками и лимитами.

### ModelClient

Внутренний интерфейс для работы с LLM. Первая реализация использует официальный
Python SDK OpenRouter. Форматы OpenRouter преобразуются во внутренние типы внутри
адаптера и не распространяются по остальному приложению.

### ToolRegistry и ToolExecutor

`ToolRegistry` хранит определения доступных инструментов. `ToolExecutor`
валидирует аргументы, проверяет разрешения, управляет timeout и нормализует
результаты и ошибки.

Первый набор coding-инструментов:

- чтение файлов;
- просмотр структуры проекта;
- поиск по тексту;
- применение patch;
- выполнение команд;
- просмотр Git diff.

### ContextManager

Формирует вход модели: system prompt, историю диалога, пользовательский запрос,
результаты инструментов и информацию о рабочем окружении. В дальнейшем здесь
могут появиться сжатие истории, память и поиск релевантного контекста.

### Policies

Реальные ограничения применяются кодом, а не только system prompt. Политики
управляют доступом к файловой системе и командам, подтверждением опасных
операций, лимитами и размером результатов.

### Events

Значимые действия представлены событиями: начало запуска, запрос к модели,
вызов инструмента, результат, ошибка и завершение. Сначала события используются
для логов и CLI, позднее — для трассировки, хранения и UI.

## Основные сущности

- `Session` — долгоживущий диалог;
- `Run` — обработка одного запроса пользователя;
- `Step` — один вызов модели или инструмента;
- `Message` — сообщение во внутреннем формате;
- `ToolCall` и `ToolResult` — запрос инструмента и его результат;
- `ModelRequest` и `ModelResponse` — независимые от провайдера контракты.

## Предполагаемая структура

```text
src/main_agent/
├── application/    # agent loop, context и policies
├── domain/         # внутренние сущности
├── ports/          # интерфейсы внешних зависимостей
├── adapters/       # OpenRouter, хранение, события
├── tools/          # filesystem, shell, git и будущие tool packs
├── interfaces/     # CLI и будущие интерфейсы
├── config.py
└── app.py
```

Ядро проектируется асинхронным для streaming, timeout, отмены и будущего
параллельного выполнения независимых инструментов.

## Первый MVP

Первая версия включает:

- CLI;
- хранение одной сессии в памяти;
- собственный `AgentLoop`;
- адаптер OpenRouter;
- базовый набор coding-инструментов;
- политики безопасности и лимиты;
- поток событий в консоль.

На этом этапе не нужны multi-agent orchestration, графы, векторная база,
долгосрочная память, MCP, фоновые очереди и отдельный plugin framework.

## Направление расширения

Новые возможности добавляются через инструменты, политики, prompts и адаптеры,
не изменяя основной цикл. Это позволит развивать coding assistant в более общий
персональный или исследовательский агент.
