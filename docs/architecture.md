# Архитектура ThoughtMate2

Веб-чат отправляет запросы в FastAPI через Nginx. Каждый `POST /api/v1/invoke?message=…` запускает один агентный цикл. Для продолжения диалога API загружает контекст модели из PostgreSQL по `session_id`.

База знаний общая для всех сессий и workspace. Конспекты Markdown индексируются отдельной CLI-командой, а агент получает фрагменты через инструмент `search_knowledge`. Векторы и тексты фрагментов хранятся в Qdrant. PostgreSQL хранит историю диалогов.

## Сессии диалога

- При запросе без `session_id` API создаёт UUID диалога и выбирает рабочий каталог из `config.yaml`. При наличии `session_id` он загружает историю и имя каталога из таблицы `session`.
- После запуска API добавляет сообщения текущего хода к сохранённому контексту. История хранится в `messages` как `JSONB`. Транзакция коммитится до отправки ответа с `session_id`.
- Параллельный запрос к той же сессии получает `409`. Активные сессии отслеживаются в памяти процесса Uvicorn.
- При старте приложение создаёт таблицу при необходимости и добавляет `workspace`, если колонки ещё нет. Сессии без сохранённого имени получают текущий workspace по умолчанию при следующем сохранении.

## Агентный цикл

1. `AgentCore.invoke()` генерирует UUID запуска, привязывает файловые инструменты к workspace сессии и формирует `messages` из системного промпта, истории и запроса пользователя.
2. `OpenRouterProvider.invoke()` отправляет `messages` и `LLM_TOOLS` в OpenRouter с `tool_choice="auto"`. Из первого варианта ответа он берёт сообщение SDK целиком. В `LLMResponse` также попадают длительность вызова, токены и стоимость. Провайдер отображает `prompt_tokens` в `input_tokens`, а `completion_tokens` — в `output_tokens`.
3. Агент учитывает метрики вызова и проверяет `message.tool_calls`. Если есть вызовы, он добавляет полное сообщение модели в `messages` и выполняет инструменты последовательно. Аргументы декодируются из JSON. Если результат функции является awaitable, агент ожидает его через `await`. Обработанная ошибка инструмента возвращается модели как строка `Error: …`.
4. Результат каждого инструмента добавляется в `messages` с ролью `tool` и исходным `tool_call_id`. Следующий вызов модели получает обновлённый список. Если вызовов инструментов нет, агент завершает запуск со статусом `completed` при наличии текста или `empty_response` при его отсутствии. Исчерпание `agent_max_steps` даёт статус `step_limit`.

`messages` хранит контекст для SDK. Отдельный список `AgentResponse.history` содержит текст модели или `null` на шагах с инструментами, результаты инструментов и финальный текст при `completed`.

## Граница провайдера и агента

`LLMResponse` описывает один вызов модели. `AgentResponse` описывает весь запуск и содержит UUID, статус, провайдера, модель, число вызовов, суммарные токены, стоимость, длительность и историю. HTTP-обработчик добавляет к результату `session_id` и `workspace`.

`AgentCore` читает у провайдера `name` и `llm_config.model`. Контекст типизирован через `ChatMessagesTypedDict` из OpenRouter SDK, а цикл использует поля и `model_dump()` сообщения SDK. Эти зависимости нужно учитывать при добавлении другого провайдера.

В конфигурации используй `llm_config.stream: false`. При отсутствии токенов или стоимости сложение метрик может завершиться HTTP 500. На нескольких шагах итоговая `duration` завышена, потому что на каждом шаге агент прибавляет время, прошедшее от начала запуска.

## Файловые инструменты

| Инструмент | Аргументы модели | Результат |
| --- | --- | --- |
| `find_files` | `pattern` | Отсортированные пути относительно workspace. Шаблон вроде `*.py` сопоставляется с именем файла. |
| `read_file` | `path` | Содержимое UTF-8 файла по пути относительно workspace. |
| `write_file` | `path`, `content` | Путь сохранённого UTF-8 файла относительно workspace, включая подкаталог `<run_id>/`. |

`workspace` — ключ в `workspaces`. Относительные пути в конфигурации отсчитываются от корня репозитория. Файловые функции отклоняют неизвестные имена workspace, абсолютные пути в вызовах и пути, которые после разрешения симлинков выходят за пределы разрешённого корня. Поиск пропускает файлы-симлинки и не спускается в каталоги по симлинкам.

Запись дополнительно ограничена подкаталогом `<run_id>/` выбранного workspace. Идентификатор общий для всех шагов одного `invoke()`. `write_file` создаёт нужные каталоги при записи. Возвращённый путь можно передать в `read_file` или повторно в `write_file` в рамках того же запуска. Чтение и поиск охватывают весь workspace.

## Глобальная база знаний

Модуль `knowledge` отвечает за чтение, нарезку, эмбеддинги, хранение и поиск. Модуль `tools/knowledge.py` предоставляет поиск агенту. `build_tools()` регистрирует эту функцию напрямую. Выбранный workspace и UUID запуска на область поиска не влияют.

Настройки находятся в `agent_config.knowledge`.

| Поле | Назначение |
| --- | --- |
| `sources` | Каталоги с исходными конспектами Markdown. Относительные пути разрешаются от текущего рабочего каталога процесса. |
| `qdrant_url` | Адрес Qdrant. В сети Compose используется `http://qdrant:6333`. |
| `collection_alias` | Стабильное имя для поиска, указывающее на опубликованную коллекцию. |
| `embedding_model` | Модель OpenRouter для эмбеддингов документов и поисковых запросов. |
| `top_k` | Максимальное число фрагментов в результате поиска. |

### Индексация и публикация

Индексатор запускается отдельно от API. Из корня репозитория команды выглядят так.

```bash
uv run python -m src.main_agent.knowledge.index --dry-run
uv run python -m src.main_agent.knowledge.index
```

1. Для каждого каталога из `sources` индексатор рекурсивно читает непустые файлы `*.md` в UTF-8. `source` содержит путь относительно каталога-источника, `title` — имя файла без расширения.
2. Markdown разбирается через `markdown-it-py`. Заголовки задают иерархию `section`. Остальные блоки собираются во фрагменты с целевым размером до 4000 символов. Отдельный большой блок может превышать этот размер, поскольку код, список, таблица или абзац сохраняются целиком.
3. `--dry-run` выводит число документов и фрагментов, их происхождение, разделы и текст, затем завершает работу до обращения к OpenRouter и Qdrant.
4. Для каждого фрагмента формируется текст из названия документа, пути раздела и содержимого. OpenRouter SDK получает эмбеддинги последовательными пакетами по 16 текстов. Реализация проверяет индексы результатов, наличие векторов и их размерность.
5. `write_collection()` записывает точки с идентификаторами `uuid4` и метрикой cosine. Размерность коллекции определяется по эмбеддингам. Запись выполняется пакетами по 64 точки с `wait=True`, после чего проверяется точное количество точек.
6. `publish_collection()` переключает `collection_alias` на возвращённую коллекцию. Удаление прежнего alias и создание нового передаются одним запросом обновления aliases. Старые коллекции остаются в Qdrant.

В текущем `write_collection()` создание коллекции и запись находятся внутри цикла по фрагментам. При N фрагментах создаются N коллекций с накопленными наборами от 1 до N точек. Индексатор публикует последнюю коллекцию, содержащую все фрагменты. Это дефект текущей реализации, который увеличивает время индексации и расход хранилища.

Каждая точка содержит вектор и payload.

| Поле payload | Содержимое |
| --- | --- |
| `source` | Относительный путь исходного документа. |
| `title` | Название документа из имени файла. |
| `section` | Список заголовков от родительского раздела к вложенному. |
| `chunk_no` | Номер фрагмента внутри документа. |
| `text` | Текст фрагмента. |
| `embedding_model` | Модель, использованная при индексации. |

Индексация полностью пересчитывает эмбеддинги. Инкрементальное обновление и автоматическая очистка коллекций отсутствуют. При нескольких каталогах одинаковые относительные пути могут совпадать в `source`. После смены модели эмбеддингов требуется повторная индексация, чтобы запросы и документы сравнивались в одном векторном пространстве.

### Поиск и подключение к агенту

1. Модель вызывает `search_knowledge` с аргументом `query`. Схема инструмента находится в `LLM_TOOLS`, функция — в `tools/knowledge.py`.
2. На время вызова инструмент создаёт `AsyncQdrantClient` и асинхронный клиент OpenRouter. `search_chunks()` получает один эмбеддинг запроса той же моделью, которая указана для индексации.
3. Поиск обращается к `collection_alias` через `query_points` с ограничением `top_k`. Qdrant возвращает payload и оценку сходства без векторов.
4. Результат содержит `score`, `source`, `title`, `section`, `chunk_no` и `text`. Агент сериализует список в JSON и добавляет его в контекст модели как результат инструмента.
5. Клиенты закрываются после вызова. При исключении инструмент пишет traceback в лог и возвращает модели строку `Error: Knowledge search is temporarily unavailable.`

Системный промпт предписывает сначала обращаться к базе знаний при любом вопросе об алгоритмах. Если ответ использует найденные материалы, модель должна явно сообщить об использовании базы знаний на языке пользователя и указать источник и раздел. При недостаточности материалов она должна обозначить это и отделить дополнения из общих знаний. Эти правила задаются промптом, отдельной программной проверки их выполнения нет.

Поиск возвращает ближайшие фрагменты без порога `score` и дополнительного ранжирования. Наличие результатов само по себе не подтверждает, что они отвечают на вопрос. Токены и стоимость эмбеддингов в метрики `AgentResponse` не включаются.

Для ручной проверки используется CLI поиска.

```bash
uv run python -m src.main_agent.knowledge.search "Почему поиск в отсортированном массиве быстрее?"
```

## Docker Compose

| Сервис | Назначение |
| --- | --- |
| `chat-ui` | Nginx раздаёт статику на `127.0.0.1:3000` и проксирует `/api/v1/invoke` в `app:8080`. |
| `app` | FastAPI на порту `8080`. Рабочая директория `/app`, пользователь `appuser`. Ключ OpenRouter передаётся через `.env`. Каталог `./tmp` монтируется в `/app/tmp`, конспекты `./knowledge` — в `/app/knowledge` только для чтения. |
| `postgres` | PostgreSQL 17. Данные сессий хранятся в именованном томе `postgres_data`. `app` запускается после успешной проверки готовности базы. |
| `qdrant` | Образ `qdrant/qdrant:v1.20.1-unprivileged`, HTTP-порт `6333`. Индекс хранится в именованном томе `qdrant_data`, смонтированном в `/qdrant/storage`. |

Конфигурация Compose задана в [docker-compose.yaml](../docker-compose.yaml). Образ `app` собирается из [thougth-mate.dockerfile](../infra/thougth-mate.dockerfile) и включает `src/main_agent/config/config.yaml`.

Qdrant запускается отдельным сервисом и не указан в `depends_on` приложения. При запуске только `app` или `chat-ui` его нужно поднять явно. Индексацию внутри контейнера выполняют из `/app` через `uv run python -m src.main_agent.knowledge.index`. Каталог `knowledge` доступен индексатору через том, а клиенты поиска создаются внутри инструмента при обращении к базе. Lifespan API управляет подключением к PostgreSQL.
