# Чек-лист развития ThoughtMate2

Нумерация соответствует [плану развития](plan.md). Отмечай задачу после выполнения, проверку — после прогона, этап — когда выполнены его критерии готовности.

## Прогресс по этапам

- [ ] Этап 0. Локальный, облачный и смешанный профили проходят проверки.
- [ ] Этап 1. Чат отвечает по базе знаний с источниками за один вызов чат-модели.
- [ ] Этап 2. Помощник находит код в workspace, объясняет его и предлагает применимый diff.
- [ ] Этап 3. Локальный агент проходит цепочку «найти → прочитать → сохранить» и показывает результат.

## Этап 0. Настраиваемые провайдеры чата и эмбеддингов

### 0.1. Выбор пользователя и конфигурация

- [ ] Сохранить выбор чат-провайдера в `llm_config.provider` и добавить поддержку `ollama`.
- [ ] Добавить в секцию `knowledge` независимый выбор провайдера эмбеддингов.
- [ ] Для существующего облачного конфига использовать OpenRouter, если провайдер эмбеддингов опущен.
- [ ] Настраивать адрес и модель отдельно для чата и эмбеддингов.
- [ ] Настраивать лимит генерации и размер контекста чата для провайдеров, которые их поддерживают.
- [ ] Проверять ключ OpenRouter при выборе OpenRouter для чата или эмбеддингов.
- [ ] Убрать обязательную зависимость от файла `.env` при полностью локальном запуске, включая запуск через Compose.
- [ ] Сделать ошибку выбранного провайдера видимой пользователю. Менять провайдера только по настройке пользователя.

### 0.2. Контракты, адаптеры и сборка

- [ ] Описать внутренний контракт чата с сообщениями, схемами инструментов, текстом ответа, вызовами инструментов и метриками.
- [ ] Учесть ответы с вызовом инструмента и пустым текстом, а также отсутствующие значения стоимости и отдельных счётчиков токенов.
- [ ] Убрать типы OpenRouter SDK из контракта и `AgentCore`. Преобразовывать сообщения и ответы внутри адаптера.
- [ ] Описать контракт пакетных эмбеддингов с сохранением порядка входных текстов.
- [ ] Адаптировать существующие вызовы чата и эмбеддингов OpenRouter под общие контракты.
- [ ] Собрать выбор адаптеров по конфигу в фабрике и передавать готовый чат-провайдер в API.
- [ ] Использовать одну сборку провайдера эмбеддингов для индексатора, CLI поиска и `search_knowledge`.
- [ ] Проверить чтение и продолжение сохранённой сессии с обычными репликами.
- [ ] Проверить чтение и продолжение сохранённой сессии с вызовами и результатами инструментов.
- [ ] Описать точки расширения для будущего GigaChat API или OpenAI: адаптер нужного контракта, настройки и регистрация. Проверить, что для добавления провайдера не нужно менять `AgentCore` и сценарии.

### 0.3. Ollama, запуск и замеры

- [ ] Подключить чат Ollama через `/api/chat` и преобразовать ответ в общий контракт.
- [ ] Подключить пакетные эмбеддинги Ollama через `/api/embed`. Проверить соответствие векторов входным текстам.
- [ ] Собрать новую коллекцию Qdrant локальной моделью. Проверить, что поисковые запросы кодируются той же моделью.
- [ ] Прогнать контрольные поисковые запросы по новой коллекции и переключить алиас после проверки.
- [ ] Подготовить примеры локального и облачного конфигов. Описать адрес Ollama в Compose и при прямом запуске API.
- [ ] Исправить `duration`, измерив полное время от начала до завершения запуска один раз.
- [ ] Записать для контрольных запросов число вызовов, входные и выходные токены, задержку первого и повторного запросов.

### Приёмка этапа 0

- [ ] **Ollama / Ollama.** Без файла `.env` и ключа OpenRouter запустить чат, продолжить сессию, выполнить индексацию и поиск. Убедиться, что оба типа запросов идут в локальный Ollama.
- [ ] **OpenRouter / OpenRouter.** На существующем конфиге проверить чат, индексацию, поиск и агентный цикл с вызовами инструментов.
- [ ] **OpenRouter / Ollama.** Проверить, что чат обращается к OpenRouter, а индексация и поиск обращаются к Ollama.
- [ ] Остановить Ollama во время проверки локального профиля. Убедиться, что пользователь видит ошибку и облачный запрос не отправляется.

## Этап 1. Помощник по базе знаний

### 1.1. Поиск в бэкенде

- [ ] Добавить режим «База знаний» в существующий чат и передавать его в `POST /api/v1/invoke`.
- [ ] Проверить, что запрос без режима использует существующий сценарий API.
- [ ] В режиме базы знаний вызывать `search_chunks()` до обращения к чат-модели и передавать результаты поиска в запрос к ней.
- [ ] Для короткого уточнения учитывать предыдущий содержательный вопрос той же сессии.

### 1.2. Контекст, источники и ошибки

- [ ] Сохранять полную историю в PostgreSQL. Передавать модели только релевантную часть диалога.
- [ ] Убирать повторяющиеся выдержки и ограничивать суммарный объём фрагментов в запросе к модели.
- [ ] Присваивать фрагментам короткие идентификаторы и сопоставлять ссылки из ответа модели с метаданными поиска.
- [ ] Показывать в чате документ, раздел и ссылку на использованный источник. Проверить, что неизвестный идентификатор не превращается в источник.
- [ ] Показывать нехватку материала, если поиск отработал, но подходящих фрагментов нет.
- [ ] Показывать недоступность поиска при сбое Qdrant или провайдера эмбеддингов. Проверить, что этот статус отличается от пустой выдачи.

### 1.3. Оценка качества

- [ ] Собрать 20–30 контрольных вопросов. Для каждого указать ожидаемый документ или раздел либо отметить отсутствие материала.
- [ ] Включить прямые вопросы, переформулировки, уточнения и вопросы вне базы знаний.
- [ ] Для каждого вопроса проверить попадание нужного фрагмента в контекст.
- [ ] Отдельно проверить правильность ответа и соответствие ссылок найденным материалам. Зафиксировать, где возникли ошибки поиска или генерации.
- [ ] Сравнить две небольшие локальные модели на одинаковых фрагментах по качеству, задержке и токенам.
- [ ] Выбрать модель и рабочий бюджет контекста по результатам сравнения.

### Приёмка этапа 1

- [ ] Задать вопрос «Почему бинарный поиск быстрее линейного?». Проверить нужный конспект, ответ за один вызов чат-модели и ссылку на источник.
- [ ] Продолжить вопросом «А откуда берётся логарифм?». Проверить, что поиск сохраняет тему предыдущей реплики.
- [ ] Прогнать первый сквозной сценарий до этапа 2: локальные эмбеддинги → новая коллекция Qdrant → режим «База знаний» → ответ через Ollama со ссылкой на источник.
- [ ] Зафиксировать для сквозного сценария выбранный бюджет контекста, число вызовов и задержку.

## Этап 2. Помощник по коду в workspace

### 2.1. Поиск по содержимому и чтение диапазонов

- [ ] Добавить поиск через `rg` в пределах настроенного workspace с ограничением числа совпадений.
- [ ] Для каждого совпадения возвращать относительный путь, номер строки и короткий фрагмент.
- [ ] Добавить чтение заданного диапазона строк с исходной нумерацией и лимитом объёма.
- [ ] Переиспользовать ограничения существующих файловых функций и проверить отклонение пути за пределами workspace.
- [ ] Для запросов с точным именем класса, функции или настройки сначала выполнять текстовый поиск по этому имени.
- [ ] Для запросов по описанию получать от модели несколько поисковых терминов и искать совпадения в бэкенде.

### 2.2. Сценарии чата

- [ ] Реализовать сценарий «Объяснить код». Найти совпадения, прочитать подходящие диапазоны и передать их модели.
- [ ] Показать в объяснении файлы и строки, подтверждающие вывод.
- [ ] Реализовать сценарий «Предложить изменение». Передать релевантные фрагменты и получить небольшой diff.
- [ ] Проверить применимость diff к текущим файлам workspace и показать его пользователю для просмотра.
- [ ] Проверить обработку случая, когда файл изменился после чтения и предложенный diff больше не применим.

### 2.3. Проверка на ThoughtMate2 и приёмка

- [ ] Прогнать вопросы по API, сессиям, провайдерам и индексации. Включить поиск по точному символу и по смыслу.
- [ ] На вопрос «Где сессия привязывается к workspace?» получить объяснение, которое связывает выбор каталога в API с сохранением в слое сессий.
- [ ] Сверить пути, номера строк и выводы в контрольных ответах с исходниками.
- [ ] Получить применимый diff для небольшой правки и проверить, что чат показывает его для просмотра.

## Этап 3. Агентный режим с коротким циклом

### 3.1. Вызовы инструментов через Ollama

- [ ] Обработать вызов инструмента от Ollama, выполнить функцию и связать результат с исходным вызовом.
- [ ] Передать результат обратно модели и получить следующий вызов или финальный ответ.
- [ ] Проверить, что ответ с вызовом инструмента и пустым текстом продолжает цикл.
- [ ] Переиспользовать реестр функций для поиска, чтения диапазона и записи результата. Отправлять модели схемы только доступных функций.
- [ ] Проверять имя инструмента и аргументы перед выполнением. Передавать модели короткую ошибку, пригодную для исправления вызова.

### 3.2. Бюджеты и фактический результат

- [ ] Ограничить число вызовов модели, суммарный объём результатов инструментов и длительность запуска.
- [ ] Проверить остановку при достижении каждого лимита. Подобрать значения для коротких цепочек по результатам прогонов.
- [ ] Останавливать повторный одинаковый неуспешный вызов. Проверить, что изменённые аргументы позволяют продолжить работу в пределах бюджета.
- [ ] Показывать причину остановки и результат уже выполненных действий.
- [ ] Переиспользовать запись в каталог `<run_id>` и передавать в чат путь из результата `write_file`.

### 3.3. Контрольные цепочки и приёмка

- [ ] **Успех.** Попросить найти пример конфига, прочитать его и сохранить вариант для Ollama. Сверить содержимое и путь созданного файла, выполненные действия и статус в чате.
- [ ] **Восстановление.** Прогнать сценарий, в котором первый поиск ничего не находит. Проверить, что агент меняет запрос и продолжает в пределах бюджета.
- [ ] **Файл отсутствует.** Проверить, что агент сообщает причину остановки и показывает доступный результат.
- [ ] **Лимит исчерпан.** Проверить, что чат отображает причину остановки, выполненные действия и итоговый статус.
