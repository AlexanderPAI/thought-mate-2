# План развития ThoughtMate2

ThoughtMate2 должен работать с небольшой локальной LLM через Ollama без оплаты токенов. Пользователь может выбрать OpenRouter, если ему удобнее пользоваться облачной моделью. Первый рабочий сценарий — ответы по собственным конспектам. Затем появится помощь с кодом в настроенном workspace, после неё — короткий агентный цикл с инструментами.

| Этап | Результат |
|---|---|
| 0. Провайдеры | Один экземпляр ThoughtMate2 запускается с Ollama или OpenRouter по настройкам пользователя. |
| 1. База знаний | Чат отвечает по конспектам с источниками за один вызов чат-модели. |
| 2. Помощник по коду | Чат находит реализацию, объясняет её со ссылками на строки и предлагает небольшие изменения в виде diff. |
| 3. Агентный режим | Агент сам выбирает следующий шаг, использует доступные инструменты и сообщает результат выполненных действий. |

Текущее устройство проекта описано в [архитектуре](architecture.md). Команды запуска и индексации приведены в [README](../README.md).

## Этап 0. Настраиваемые провайдеры чата и эмбеддингов

### 0.1. Выбор пользователя и конфигурация

- Выбирать провайдеров в `config.yaml` для экземпляра приложения. Сохранить `llm_config.provider` для чата и добавить настройку провайдера в секцию `knowledge` для эмбеддингов.
- Сохранить поведение существующих конфигураций OpenRouter. Если провайдер эмбеддингов в такой конфигурации опущен, использовать OpenRouter. В готовом локальном примере явно указать Ollama в обеих настройках.
- Указывать модель и адрес сервера для каждого компонента. Для чата сохранить отдельные настройки лимита генерации и, где поддерживается, размера контекста.
- Требовать ключ OpenRouter только для выбранного компонента. Проверить, что запуск приложения и входные точки базы знаний в полностью локальном профиле не зависят от наличия файла `.env`.
- При ошибке выбранного провайдера возвращать понятное сообщение. Переключение между локальным и облачным API происходит по явному выбору пользователя.

| Профиль | Чат | Эмбеддинги |
|---|---|---|
| Локальный | Ollama | Ollama |
| Облачный | OpenRouter | OpenRouter |
| Смешанный | OpenRouter | Ollama |

### 0.2. Общие контракты и сборка зависимостей

- Сохранить роль существующего `LLMProvider` и убрать типы SDK OpenRouter из контракта и `AgentCore`. Контракт чата должен описывать сообщения, схемы доступных инструментов, текст, вызовы инструментов и метрики. Учесть, что вызов инструмента может приходить без текста, а стоимость и отдельные показатели токенов зависят от провайдера.
- Выделить контракт эмбеддингов. Адаптер принимает пакет текстов и возвращает векторы в порядке входных данных. Индексатор, CLI поиска и инструмент `search_knowledge` используют его через общую конфигурацию.
- Собирать адаптеры по именам провайдеров в фабрике. FastAPI получает готовые зависимости при запуске. Команды индексации и поиска используют ту же сборку для эмбеддингов.
- Преобразовывать форматы сообщений и ответов внутри адаптеров. При переходе на внутренний формат проверить чтение уже сохранённых историй, в том числе реплик с вызовами инструментов.
- Зафиксировать порядок подключения нового провайдера. Для GigaChat API или OpenAI потребуется адаптер нужного контракта, его настройки и регистрация в фабрике. Чат и эмбеддинги можно добавлять независимо. Реализация этих провайдеров выходит за рамки этапа.

### 0.3. Подключение и проверка профилей

- Подключить чат Ollama через `/api/chat`, эмбеддинги через `/api/embed`. Проверить обычный ответ, продолжение диалога, индексацию и поиск. Сквозной цикл инструментов через Ollama проверить на этапе 3.
- При смене модели эмбеддингов построить отдельную коллекцию Qdrant. Использовать одну модель для документов и запросов, проверить контрольные результаты и затем переключить алиас.
- Проверить исходные сценарии через OpenRouter, включая вызовы инструментов. Отдельно проверить, что в смешанном профиле генерация идёт через OpenRouter, а индексация и поиск используют Ollama.
- Описать настройку адреса Ollama при запуске приложения через Compose и при запуске API напрямую. Подготовить примеры локального и облачного конфигов.
- Исправить расчёт `duration` в агентном цикле. Измерять длительность запуска один раз от начала до завершения. На контрольных запросах сохранять число вызовов, входные и выходные токены, задержку первого запроса после загрузки модели и задержку повторного запроса.

**Критерий готовности.** Локальный профиль без ключа OpenRouter проходит чат, индексацию и поиск. Облачный профиль сохраняет текущие сценарии. Смешанный профиль направляет оба типа запросов к выбранным провайдерам. Подключение нового провайдера укладывается в добавление адаптера, настроек и записи в фабрике.

## Этап 1. Помощник по базе знаний

### 1.1. Запускать поиск в бэкенде

- Добавить в существующий чат режим «База знаний» и передавать его в `POST /api/v1/invoke`. Запросы без режима продолжают работать через существующий сценарий API.
- В режиме базы знаний выполнять поиск до вызова чат-модели. Переиспользовать `search_chunks()` и метаданные Qdrant.
- Для короткого уточнения учитывать предыдущий содержательный вопрос сессии. Проверить, что запросы «Почему бинарный поиск быстрее линейного?» и «А откуда берётся логарифм?» находят материалы по одной теме.

### 1.2. Ограничить контекст и показать источники

- Сохранять полную историю в PostgreSQL и включать в запрос к модели только нужную часть диалога. Ограничивать общий объём фрагментов, убирая повторяющиеся выдержки.
- Передавать фрагменты с короткими идентификаторами. Связывать ссылки в ответе с фактическими метаданными поиска. Показывать в UI документ и раздел, использованные в ответе.
- Различать отсутствие подходящего материала и сбой поиска. При пустой выдаче сообщать о нехватке материала, при ошибке Qdrant или эмбеддингов показывать недоступность поиска.

### 1.3. Оценить поиск и ответы

- Подготовить 20–30 вопросов из Markdown-конспектов с ожидаемыми документами или разделами. Включить прямые вопросы, переформулировки, уточнения и темы, которых в базе нет.
- Отдельно проверять попадание нужного источника в выдачу и качество ответа на основе найденного текста. Для каждого сбоя определять, произошёл он на поиске или на генерации.
- Сравнить две небольшие локальные чат-модели на одинаковых фрагментах. По качеству ответов, задержке и токенам выбрать модель и рабочий бюджет контекста.

**Критерий готовности.** ThoughtMate2 находит нужный конспект, отвечает за один вызов чат-модели и показывает источник. Уточняющий вопрос сохраняет тему. Отсутствие материала и сбой поиска имеют разные статусы.

## Этап 2. Помощник по коду в workspace

### 2.1. Добавить поиск по содержимому и чтение диапазонов

- Добавить поиск по содержимому файлов в настроенном workspace. Использовать `rg` с ограничением числа совпадений. Возвращать путь относительно workspace, номер строки и короткий фрагмент.
- Добавить чтение диапазона строк с нумерацией. Переиспользовать ограничения путей существующих файловых функций и ограничить объём возвращаемого текста.
- Начинать с текстового поиска, если запрос содержит точное имя класса, функции или настройки. Для запроса по описанию дать модели подобрать несколько поисковых терминов и выполнить поиск по ним в бэкенде.

### 2.2. Реализовать два сценария чата

1. **Объяснить код.** Найти совпадения, прочитать подходящие диапазоны и передать их модели. В ответе показать файлы и строки, на которых основано объяснение.
2. **Предложить изменение.** Передать модели релевантные фрагменты и получить небольшой diff. Проверить применимость diff к текущему содержимому workspace и показать его пользователю для просмотра.

### 2.3. Проверить на коде ThoughtMate2

- Взять вопросы по API, сессиям, настройкам провайдеров и индексации. Проверить запросы по символу и по смыслу.
- Для объяснений сверять пути, строки и выводы с исходным кодом. Для предложенных правок проверять применимость diff и обработку случая, когда исходный файл успел измениться.

**Критерий готовности.** На вопрос «Где сессия привязывается к workspace?» помощник находит выбор каталога в API и сохранение в слое сессий. На небольшую правку выдаёт diff, применимый к текущей версии файла.

## Этап 3. Агентный режим с коротким циклом

### 3.1. Провести вызовы инструментов через Ollama

- Проверить полный обмен сообщениями. Модель вызывает инструмент, бэкенд выполняет функцию, результат связывается с вызовом и передаётся модели. Покрыть случай, когда текст в ответе модели пустой.
- Передавать в провайдер схемы только доступных в текущем запуске функций. Переиспользовать существующий реестр и начать с поиска, чтения диапазона и записи результата.
- Проверять имя и аргументы до выполнения. Возвращать модели короткое описание ошибки, по которому она сможет исправить следующий вызов.

### 3.2. Ограничить выполнение и показать результат

- Задать бюджеты на число вызовов модели, объём результатов инструментов и время запуска. Начать с коротких цепочек и выбирать лимиты по результатам проверок.
- Останавливать повторение одинакового неуспешного вызова. При достижении лимита показывать причину остановки и результат уже выполненных действий.
- Использовать существующую запись в каталог `<run_id>`. Отдавать в чат путь из фактического результата `write_file`.

### 3.3. Проверить контрольные цепочки

| Сценарий | Ожидаемый результат |
|---|---|
| Найти пример конфига, прочитать и сохранить локальный вариант для Ollama | Агент создаёт файл, чат показывает путь и статус. |
| Первый поиск не дал совпадений | Агент уточняет запрос и продолжает в пределах бюджета. |
| Исходного файла нет или исчерпан лимит | Чат показывает причину остановки и доступный результат. |

**Критерий готовности.** Небольшая локальная модель выполняет цепочку «найти → прочитать → сохранить», а чат показывает созданный файл, выполненные действия и итоговый статус.

## Первый сквозной сценарий

Локальные эмбеддинги → новая коллекция Qdrant → режим «База знаний» → ответ через Ollama со ссылкой на источник. Его стоит пройти до добавления поиска по коду. По нему можно проверить полностью локальный запуск, измерить задержку и выбрать размер контекста для следующих этапов.
